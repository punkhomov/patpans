# patpans

Программный Snap Tap / SOCD-cleaner: при одновременном удержании противоположных клавиш движения активной остаётся последняя нажатая, а предыдущая автоматически отпускается. Идейный аналог [SnapKey](https://github.com/cafali/SnapKey), но в виде CLI с общим ядром для Linux и Windows.

> **Дисклеймер.** patpans вмешивается в системный ввод, и этот факт можно обнаружить (см. раздел «Обнаружимость ввода»). Использование инструмента в играх, где Snap Tap/SOCD-эмуляция запрещена правилами, не рекомендуется: анти-чит может распознать инъекцию, что приведёт к бану аккаунта, кику или другим последствиям. Ответственность за использование лежит на вас.

## Возможности

- Группы клавиш по умолчанию: `A`/`D` и `W`/`S`, свои группы задаются в конфиге.
- Sticky-восстановление: если отпустить перекрывшую клавишу, ранее удержанная снова становится активной.
- Клавиши вне групп проходят без изменений, автоповтор пробрасывается только для активной клавиши.
- Хоткей вкл/выкл (по умолчанию `F8`) с корректным ресинком состояния при переключении.
- Бэкенды: Linux (`evdev` + `uinput`), Windows (низкоуровневый хук `WH_KEYBOARD_LL` + `SendInput`, без драйверов).
- Демон + клиенты: перехват живёт в демоне, CLI (и будущий GUI) — клиенты по локальному сокету: `status`, `toggle`, `enable`, `disable`, `reload`, `stop`.
- Portable: конфиг и лог рядом с исполняемым файлом, без установки и реестра; single-instance через сокет/мьютекс.
- Системный трей (`tray-icon`): иконка on/off, галочка «Snap Tap enabled» и «Quit patpans» в меню; состояние синхронизировано с хоткеем `F8`. Отключается флагом `--no-tray` или `tray = false`.
- Режим `simulate` — прогон сценария без железа; `check` — валидация конфига и диагностика окружения.

## Требования

- Rust nightly — `rust-toolchain.toml` фиксирует канал (MSRV 1.95: столько требует `eframe`/`egui` для feature `gui`).
- Linux: доступ к `/dev/input/*` и `/dev/uinput` (root или группа `input` + udev-правило), ядро с `uinput`. Трей работает через D-Bus (`ksni`-бэкенд, GTK не нужен); без сессионного D-Bus `run` предупредит и продолжит без иконки.
- Windows: дополнительных драйверов не нужно; если игра запущена от администратора, patpans тоже нужно запускать от администратора.

## Сборка и запуск

```console
cargo build --release

cargo run -- run                    # демон: перехват + IPC + трей
cargo run -- status                 # состояние демона
cargo run -- toggle                 # вкл/выкл перехват
cargo run -- enable                 # включить
cargo run -- disable                # выключить
cargo run -- reload                 # перечитать конфиг
cargo run -- stop                   # остановить демон
cargo run -- simulate --builtin sticky
cargo run -- check
```

Конфиг по умолчанию — `patpans.toml` рядом с исполняемым файлом (создаётся при первом `run`); лог пишется в `patpans.log` там же (при достижении 1 МиБ ротируется в `patpans.log.old`). Путь можно переопределить флагом `--config <PATH>`, IPC-эндпоинт — флагом `--socket <ENDPOINT>` или переменной `PAT_PANS_SOCKET`/`PAT_PANS_PIPE`.

## GUI

```console
cargo build --release --features gui   # соберёт patpans-gui и patpans
```

`patpans-gui` — простое окно настроек: статус демона (ON/OFF, elevated), Start/Stop, хоткей (список + «Capture»), sticky, редактор групп, трей, Save/Reload. Особенности:

- трей принадлежит демону, GUI его не создаёт; закрытие окна не останавливает перехват;
- запуск демона из GUI идёт без окна консоли (Windows), лог — в `patpans.log` рядом с конфигом;
- GUI ищет `patpans`/`patpans.exe` рядом с собой, поэтому в portable-сборке держите оба файла вместе;
- «Start as administrator» (Windows) перезапускает демон через UAC — нужно для игр под elevation; демону передаются `--config` и `--socket`, так что кастомные пути не теряются;
- Save пишет в тот конфиг, с которым работает демон (путь берётся из статуса), а не в файл по умолчанию; если файл не парсится, GUI показывает ошибку и блокирует сохранение поверх.

## Релизы

GitHub Actions (`.github/workflows/ci.yml`) на каждый push в `main` собирает portable-артефакты:

- `patpans-portable-windows-x86_64.zip` — `patpans.exe`, `patpans-gui.exe`, пример конфига, README;
- `patpans-portable-linux-x86_64.tar.gz` — `patpans`, `patpans-gui`, пример конфига, README.

Там же гоняются линты, тесты и QEMU-e2e (Linux), а на Windows — сборка GUI и хук-тест (шаг advisory: для него нужен интерактивный десктоп).

## Конфиг (`patpans.toml`)

```toml
toggle = "F8"      # клавиша вкл/выкл, "none" — без хоткея
sticky = true      # возвращать удержанную клавишу после отпускания перекрывшей
tray = true        # иконка в системном трее
groups = [["A", "D"], ["W", "S"]]
```

Флаги CLI: `--config <PATH>`, `run --toggle <KEY> --groups "A,D;W,S" --no-sticky --no-tray`, `simulate --script <SCRIPT> --builtin <NAME>`. Имена клавиш — как в таблице `src/keys.rs` (`A`..`Z`, `Left`, `Space`, `F8`, ...), есть алиасы (`ctrl`, `esc`, `arrowleft`). Клавиша может входить только в одну группу — конфиг с пересечениями отклоняется.

## min-publish-age

Изначально фича была unstable (`[unstable] min-publish-age = true`), но в Cargo 1.100 она стабилизирована: на текущем nightly такого флага уже нет. Проект остаётся на nightly, а в `.cargo/config.toml` используются стабильные ключи:

```toml
[registry]
global-min-publish-age = "14 days"

[registries.crates-io]
min-publish-age = "14 days"
```

Проверка, что фильтр реально работает, — в `TESTING.md`.

## Тестирование

Логика покрыта 45 тестами (включая модель настроек GUI): юнит-тесты (правила хука, портативные пути), интеграционные сценарии на симуляторе и headless-тесты демона с IPC. Linux-бэкенд проверяется настоящим e2e через виртуальную клавиатуру `uinput` в мини-VM (`./scripts/e2e-qemu.sh`) — включая цикл Stop/Start со снятием и повторным захватом клавиатуры; Windows-бэкенд — отдельным e2e на живом Windows: `scripts/e2e-windows.ps1` (`cargo test --features testing --test windows_hook_e2e`).

Подробный отчёт: что именно проверено, как воспроизвести, что не покрыто — в [TESTING.md](TESTING.md).

## Обнаружимость ввода

patpans не пытается скрыть факт инъекции: события создаются штатными механизмами ОС и оставляют следы, видимые на разных уровнях.

| Наблюдатель | Windows | Linux |
| --- | --- | --- |
| Обычная игра | raw input: `RAWINPUTHEADER.hDevice == NULL` у синтетики (если проверяет) | устройство-источник `patpans virtual keyboard`, `BUS_USB`, vendor `0x1234` / product `0x5678`, `phys = .../virtual/inputN` |
| Приложение с низкоуровневым хуком | `LLKHF_INJECTED` / `LLKHF_LOWER_IL_INJECTED` | — |
| Перечисление устройств | — | имя, VID:PID и `phys` видны через udev/libinput/evtest |
| Анти-чит уровня драйвера | факт инъекции и процесс-источник (ETW/драйвер) | uinput-устройство, `EVIOCGRAB`, процесс |
| Оконные сообщения | `WM_KEYDOWN` / `GetAsyncKeyState` неотличимы | — |

Детали: на Windows мы шлём `wScan = 0` и `dwExtraInfo = 0`, у инъекций стоит флаг injected; на Linux сам поток `input_event` неотличим от железа, но паспорт виртуального устройства очевидно синтетический. Принципиально неотличимый ввод даёт только драйвер виртуального HID — в patpans этого нет, и использование подобных обходов против правил игр не поддерживается.

## Ограничения и предупреждения

- Linux: нужны права на `input`; захватываются все клавиатуры с нужными клавишами, возможен конфликт с другими ремапперами.
- Нет hot-plug: клавиатура, подключённая после старта, не подхватывается.
- Пробрасываются только `EV_KEY`: scancode-события (`EV_MSC`) и LED (Caps/Num Lock) не синхронизируются.
- Windows: инъекция через `SendInput` не доходит до приложений с более высокими правами (UIPI).
- Snap Tap запрещён в ряде игр, а ввод от patpans обнаружим (см. «Обнаружимость ввода»); использование может нарушать правила игры и привести к бану.
